## What is DNSSEC?

**DNSSEC** (Domain Name System Security Extensions) is a suite of extensions that adds security to the Domain Name System
(DNS)—the "phonebook" of the internet that translates website names (like `example.com`) into IP addresses.

Traditional DNS has a major flaw: it does not verify whether the data received is actually from the legitimate server. This
leaves it vulnerable to **DNS cache poisoning** or **man-in-the-middle attacks**, where a hacker redirects users to a
malicious, fake website. DNSSEC solves this by digitally signing DNS records using public-key cryptography (similar to the
RSA signatures we discussed earlier) to prove their authenticity and integrity.

---

## The DNSSEC Chain of Trust

To ensure that the digital signatures can be trusted across the entire internet, DNSSEC uses a **Chain of Trust**. This is a
hierarchical structure where each level of the DNS tree vouches for the security of the level below it.

The chain operates across four main tiers, starting from the very top and moving down to your specific website:

### 1. The Root Zone (The Anchor)

- At the very top of the hierarchy is the **DNS root zone** (`.`).
- The cryptographic keys for the root zone are protected by a global community of security experts and organizations (like
  ICANN) using rigorous, multi-party security ceremonies. This is the **Trust Anchor** from which all other trust flows.

### 2. Top-Level Domains (TLDs)

- Below the root are the TLD managers (like the entities managing `.com`, `.org`, or `.pl`).
- The root zone signs a special record (called a **Delegation Signer** or **DS record**) that verifies the public key of the
  TLD. This links the TLD's security directly back to the Root Zone.

### 3. Second-Level Domains (Your Domain)

- Below the TLD is your specific domain (e.g., `example.com`).
- The TLD registry holds a DS record that validates your domain's public key.

### 4. Individual DNS Records

- Inside your domain, your individual records (like your website's IP address `A record`) are signed with your domain's
  private key.

---

## How Verification Works in Real Time

When a user tries to visit a secured website, their resolver (like Google's `8.8.8.8` or Cloudflare's `1.1.1.1`) validates
the response step-by-step:

1. The resolver asks for the website's IP address.
2. The domain returns the IP address along with its **digital signature**.
3. The resolver checks the signature against the domain's public key.
4. It then checks that public key against the TLD's record, which checks back to the Root Zone.
5. If every link in the chain checks out, the resolver knows the data is authentic. If any signature fails or is missing, the
   resolver blocks the connection and throws a security error.
