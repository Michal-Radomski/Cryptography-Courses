The TLS handshake is the foundational negotiation process that occurs between a client (such as a web browser) and a server
before any sensitive application data can be securely transmitted. It establishes encryption parameters, verifies server
identity, and generates the unique session keys used to secure the connection.

The mechanics of the handshake vary slightly depending on whether the connection uses **TLS 1.2** or the modern **TLS 1.3**
standard.

---

### The Modern TLS 1.3 Handshake (1-RTT)

TLS 1.3 streamlined the process down to a single round-trip time (1-RTT), drastically reducing latency while enhancing
security.

1. **Client Hello:** The client sends a message containing:

- The highest TLS version it supports (TLS 1.3).
- A list of supported cipher suites (encryption algorithms).
- **Key Share:** The client's generated public parameters for the key exchange (using algorithms like ECDHE), allowing it to
  guess which key exchange algorithm the server will prefer.

2. **Server Hello, Certificate, & Key Exchange:** The server responds with:

- The chosen TLS version and cipher suite.
- Its own **Key Share** parameters.
- Its **Digital Certificate** (to prove its identity).
- A digital signature verifying the handshake parameters.

3. **Derivation of Keys & Finished:** At this exact point, **both the client and server instantly compute the shared session
   keys** using their own private parameters and the peer's public key share. The server sends a finished message, and the
   client responds likewise.
4. **Encrypted Application Data:** Encrypted data can flow immediately. Because key agreement happens alongside the initial
   greeting, TLS 1.3 cuts connection setup time in half compared to older protocols.

---

### The Legacy TLS 1.2 Handshake (2-RTT)

TLS 1.2 requires two full round-trips before application data can be sent, making it slower than TLS 1.3.

1. **Client Hello:** The client sends supported TLS versions, cipher suites, and a random client nonce.
2. **Server Hello & Certificate:** The server responds with the chosen version, cipher suite, its certificate, and a server
   nonce.
3. **Key Exchange (Client to Server):** The client verifies the certificate, generates a pre-master secret, encrypts it using
   the server's public key (found in the certificate), and sends it to the server.
4. **Session Keys Generated:** Both sides independently compute the exact same session keys from the client and server nonces
   and the pre-master secret.
5. **Finished:** Both sides exchange encrypted "Finished" messages to confirm the keys match and encryption is working.

---

### Key Cryptographic Mechanisms Within the Handshake

- **Cipher Suites:** A combination of algorithms grouped together (e.g., `TLS_AES_256_GCM_SHA384`). It defines how the key
  exchange is performed, how the traffic is encrypted (symmetric cipher), and how data integrity is verified (hash function).
- **Perfect Forward Secrecy (PFS):** Modern handshakes rely on ephemeral key exchange (like **ECDHE** - Elliptic Curve
  Diffie-Hellman Ephemeral). This ensures that even if an attacker records encrypted traffic today and steals a server's
  long-term private key years from now, they _cannot_ decrypt past sessions because the session keys were destroyed
  immediately after the connection closed.
