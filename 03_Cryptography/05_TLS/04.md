Once the TLS handshake is complete and session keys are securely established, the actual **Data Transmission** phase begins.
This stage uses the **TLS Record Protocol** to handle the secure movement of application data (such as HTTP requests and
responses) between the client and server.

### Core Mechanisms of TLS Data Transmission

- **Symmetric Encryption:** While asymmetric cryptography (like RSA or Elliptic Curve math) was used during the handshake to
  authenticate the server and exchange keys, it is too computationally expensive for continuous data flow. Data transmission
  relies entirely on **symmetric encryption** (using algorithms like AES-GCM or ChaCha20-Poly1305) governed by the session
  keys. Both sides use the exact same keys to encrypt and decrypt traffic rapidly.
- **Record Layer and Fragmentation:** Raw application data from the browser or web server is broken down into manageable
  chunks called "records." Each record is processed individually before being handed off to the underlying transport layer
  (TCP).
- **Authenticated Encryption with Associated Data (AEAD):** Modern TLS versions use AEAD ciphers, which combine encryption
  (confidentiality) and message authentication (integrity) into a single mathematical operation. This ensures that:
- **Confidentiality:** Eavesdroppers intercepting the packets only see ciphertext.
- **Integrity:** If an attacker intercepts and modifies even a single bit of the encrypted data in transit, the receiving end
  detects the tampering immediately, drops the packet, and terminates the connection.

- **Sequence Numbers and Anti-Replay:** Each TLS record is assigned a hidden sequence number. This number is factored into
  the encryption and authentication tags. It ensures that packets cannot be intercepted by an attacker, delayed, and replayed
  later to trick the server (replay attacks), and it guarantees that packets are processed in the correct order.
